# Table QR menus and guest requests

Adds local table QR menus and staff-reviewed guest order requests on top of the
existing POS and commercial licensing foundation. See the
[operation guide](../../operations/qr-ordering.md) for restaurant setup and use.
This handoff records implementation and local integration verification. No
completed cloud deployment or rebuilt desktop installer is claimed here.

## Behavior

- `/menu#<table-token>` opens the guest interface without staff authentication or
  device registration. Basic supports browsing; Pro's `qrOrdering` entitlement
  permits submissions and staff acceptance. Old signed grants without that field
  default it to false and need an updated revision to enable ordering.
- Guests must use the restaurant's LAN/Wi-Fi and a running hub. LAN URLs are the
  default QR origin; selecting loopback displays an explicit main-PC-only note.
  Internet loss is supported within existing offline-license operation.
- Guests browse active categories/products/options and submit item notes. The
  server snapshots authoritative prices/tax information; stale menus require
  review, and changed or unavailable items prevent staff acceptance.
- Tables contains the staff QR inbox and pending count. Admin/cashier/waiter
  staff explicitly select a new bill group or an open group at the same table.
  Acceptance adds pending items and opens the order; normal Send to kitchen is
  still required. Reject requires a reason shown on the guest receipt.
- Basic can read and reject prior requests after downgrade but cannot accept
  them. Staff request history retains accepted/rejected/expired rows. Each list
  returns up to 500 latest requests, and the inbox uses that same display limit.
- Admin table-code management supports enable, disable, confirmed rotation,
  allowed server-origin selection, link copying, and a dedicated printable QR
  sheet. Rotation invalidates old links. Disabling/rotating preserves prior
  requests and receipt recovery.
- Pending requests expire after two hours; ten pending requests per table;
  30 selections per request; 1–20 units per selection; notes up to 200 characters.
  Per-client-IP, per-minute process-local rates: 240 menu reads, 30 submissions
  including retries, 600 receipt reads. Submission bodies are capped at 32 KiB.

## Data and endpoints

Migration 009 (`guest-qr-ordering`) adds `table_qr` and `guest_requests`, including
request snapshots, receipt hashes, status/reviewer/order records, and idempotency
data. Existing backup/migration behavior applies. No cloud tenancy is added.

Guest endpoints are `/api/guest/menu`, POST `/api/guest/requests`, and GET
`/api/guest/requests/:id`. Table tokens use `x-qr-token`; receipt reads require the
private `x-guest-receipt` credential. Guest fetches omit staff credentials and
do not allocate staff device slots.

Staff endpoints are GET `/api/qr/tables`, PUT `/api/qr/tables/:id`, GET
`/api/qr/tables/:id/image?origin=...`, GET `/api/qr/requests?status=...`, and POST
request `accept`/`reject` actions. Only GET exists at the tables collection path;
enable/disable/rotate writes target the table ID. The image response is
`{url, qr}`, with a PNG data URL. Table-code management requires `tables.manage`;
request listing requires `orders.read`; rejection requires `orders.update`;
acceptance requires `orders.update`, `orders.create`, and `qrOrdering`.

Guest submission freezes its ID/body before sending in browser storage keyed by
the original table token. Identical retries recover the saved receipt, including
after a lost response, code rotation, or disablement. Keep the original browser
page/storage until an ambiguous submission is reconciled. Clearing storage or
switching to a new table token does not transfer its receipt credential.
Receipt polling does not depend on a still-active table code.

Staff acceptance is transactional and repeated identical decisions do not add
items twice. It does not issue bills, settle payments, create KOTs, or consume
stock. `guest-request.changed` drives inbox refresh with a 15-second poll fallback;
table/order broadcasts refresh the normal POS views. UI writes use busy guards
and preserve selected groups/rejection text on errors while pending.

## Changed areas and verification

- Server: `apps/server/src/guest-ordering.ts`, with API integration tests in
  `guest-ordering.test.ts` and application route registration.
- Domain: `guest-ordering.ts`, migration 009, and backward-compatible entitlement
  parsing/defaults in licensing.
- Guest UI: `GuestMenu.tsx`, `guest-menu.css`, and App's guest route.
- Staff UI: `QrRequests.tsx`, `qr-staff.css`, and Tables integration. QR image
  fetches use `/image`; images are bound to table/token path/origin so switching
  selection or rotating cannot display a previous code under a new table label.
  Printing uses a dedicated body portal to omit the rest of the POS page.
- Full suite: 297 tests across 43 files passed before the final printer-control
  hardening. After that change, all 75 affected QR/printing tests passed,
  including the new printer-command regression and guest control-character
  validation. Typecheck, UI production build, and whitespace checks passed.
- `tools/e2e/m8-qr.js`: 14 browser checks passed, including a deliberately lost
  successful POST response, identical safe retry, staff acceptance, and KOT stock
  deductions. `m8-qr-review.js`: 9 checks passed for stale prices, existing bill
  acceptance, rejection and receipt recovery after rotation. Mobile and desktop
  guest screens were visually inspected. No physical print or second-device LAN
  success is implied by these checks.
- A signed Basic downgrade was also checked in the browser: the guest menu
  remained readable without Add/Submit controls, while the staff inbox disabled
  bill-group selection and acceptance but retained rejection. The disposable
  fixture was returned to Pro afterward. No browser runtime errors were reported.
- Screenshots: `docs/screenshots/qr-menu-desktop.png` and
  `docs/screenshots/qr-menu-mobile.png`. QA used an isolated database on port
  4117; the pre-existing desktop server on 4100 was not rebuilt or restarted.
- Guest notes reject printer controls; `EscPos.text` renders control bytes as
  spaces so text cannot execute feed/cut/drawer commands. Dedicated print methods
  still emit printer commands. Multiline note text prints as a single safe line.

## Remaining scope

Hosted accounts, subscription renewals, cloud data synchronization, multi-tenant
public hosting, and remote ordering remain unfinished. The local single-outlet
server must not be exposed publicly as the hosted product. Wi-Fi isolation,
real-phone access, printed-code scanning, hardware printing, signed release
packaging, and clean Windows rollout still need deployment-specific checks.
