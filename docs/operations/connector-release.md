## Consent and authentication

Staff with `support.remote` can send a connector from a chat or an existing customer's page. A customer-only chat has no installation. Installation-bound browser chats retain their existing cookie authentication. Updated counters require their existing local admin/PIN authorization before opening a download; the connector asks for a separate view/control decision on the PC. Older deployed counters retain their existing protocol.

Invitation tokens and fallback codes last 30 minutes. Opening a download link does not consume it. Redemption atomically consumes either credential and returns a 15-minute consent token. Approval consumes that token, enforces the requested mode, and creates a one-use signalling credential. Decline creates no signalling credential. Approved sessions have a two-minute connection deadline and a maximum one-hour duration. The in-app 75-second request timeout does not apply to connector invitations.

Token and fallback-code registries store SHA-256 hashes only. Invitation links/codes are returned once to staff and pushed to connected chat clients; the persisted system message omits credentials. Reloading chat does not recover a secret link—use the staff dialog or create a new invitation after ending the old one. No session credentials are written into the executable cache. Operational logs contain route names, status and byte counts, never query strings, bodies, cookies or credentials.

One connector socket carries chat and signalling for exactly its session/chat. Its token cannot authenticate the old agent endpoint. Stop, socket loss, expiry and service restart end access. The connector stops after 15 seconds without a signalling heartbeat. The counter receives live audit events and replays durable session history on reconnect without duplicate log entries. A monitor/DPI configuration change ends sharing so newly arranged screens cannot be captured without the required visible frames.

## Windows bootstrap and optional admin prompts

`tools/connector-stub.nsi` requests Windows elevation once. Declining UAC exits. Filename tokens support browser `(2)` suffixes; renamed files ask for the fallback code. The bootstrap uses OS TLS validation, a signed RSA/SHA-256 release manifest, exact size and archive hashes, safe extraction paths, and timestamped Authenticode validation for production. NSIS 3.0.4.1 is obtained through electron-builder's pinned SHA-256 dependency; Electron 43.4.0 and koffi 2.16.3 are pinned. Use `npm ci` to honor the dependency lock.

`%ProgramData%\MasalaPOS\SupportConnector` is owned and writable only by administrators and SYSTEM. Existing unsafe owners, ACLs and reparse points are rejected. A verified ZIP is reused, then freshly extracted to a unique protected directory for each session. Partial downloads are removed; closing the preparation window cancels the download. A global mutex rejects duplicate launches. The launcher passes session context over stdin and runs the payload with inherited elevation. It installs no remote-control service.

Admin-prompt passthrough is **unchecked** by default. Before changing `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\PromptOnSecureDesktop`, the guardian saves its exact prior DWORD or absence and registers a SYSTEM startup task that can only restore it. Only then may it write zero and signal readiness. An independent PowerShell watchdog monitors the parent PID/start time and heartbeat. Stop, disconnect, timeout, process failure and reboot invoke restoration. Successful restoration is verified before removing recovery state. A failure keeps the marker and displays a local warning. Setup failure leaves passthrough unavailable; the person can continue with its checkbox unchecked.

Recovery files live under `recovery\`, independently of temporary payloads. The task is `MasalaPOS Support Connector Restore`. If restoration cannot be confirmed, restart Windows to retry the restore-only task, then have a local administrator inspect the saved `restore.json` and policy. Never replace the saved value with a presumed default; an absent value must be deleted again. Keep the marker and task until the previous policy is confirmed. Do not use this recovery mechanism for reconnecting support after reboot.

## Build, sign and publish

1. Run `npm ci`, `npm run typecheck`, `npm test`, and `npm run test:packaging`. Validate `infra/connector.json` with cfn-lint and `infra/connector.guard`.
2. For isolated development artifacts, run `npm run build:connector:dev`. They cannot pass production publication. For production, provide `CONNECTOR_MANIFEST_KEY_FILE` (release-signing RSA private key, separate from the CDN key), `CONNECTOR_CERT_SHA1`, `CONNECTOR_SIGNTOOL`, and `CONNECTOR_CDN_URL`; run `npm run build:connector`.
3. The builder signs the Electron executable before packaging, verifies its timestamped signature, creates the ZIP and signed release manifest, then signs/verifies the small stub. Hashes are computed only after signing. The manifest binds version, size, SHA-256, URL and production status. Preserve the protected release key offline or in the signing pipeline, never in Git or the portal.
4. Copy `tools/connector-acceptance.example.json` to a private release record and complete every real-PC check for the **exact version/hash**. Supply its path as `CONNECTOR_ACCEPTANCE_FILE`. Do not check off simulated or unperformed tests.
5. Set `CONNECTOR_S3_BUCKET`, `CONNECTOR_DISTRIBUTION_ID`, `CONNECTOR_CDN_URL` and a separate publisher AWS profile. Run `npm run publish:connector`. It refuses incomplete acceptance and unsigned/development builds; uploads immutable artifacts first and promotes `latest.json` last. `-- --staging` only writes a protected staging prefix and does not enable the portal. Do not overwrite a version with different bytes.
6. Use `tools/verify-connector-distribution.mjs` with the CDN, bucket, key ID, manifest, a securely supplied CDN private key file and optional `CONNECTOR_ARTIFACT_PREFIX`. It checks signed filename isolation, modified/expired signatures, unsigned staging denial, runtime size/hash and direct-S3 denial. Remove temporary local CDN-key files after verification.
7. Only after signing and acceptance, atomically copy the approved manifest to a root-managed path on the portal and configure `CONNECTOR_MANIFEST_FILE`, `CONNECTOR_CDN_URL`, `CONNECTOR_CDN_KEY_ID`, `CONNECTOR_CDN_KEY_PARAMETER`, `AWS_REGION=us-east-2` and the SSM-only identity. Then change `CONNECTOR_ENABLED=1` and restart the service. The portal refuses a development manifest or a runtime URL outside its configured release location.

The current staging artifacts validate packaging/distribution. They intentionally do not activate the live invitation/manifest endpoints. For interactive development use a separate test backend and build with its HTTPS `CONNECTOR_ORIGIN`; never point an unsigned test runtime at enabled restaurant distribution.

## Deployment and rollback

Build the portal and Node host using their workspace build commands. Archive only `main.mjs`, `main.mjs.map`, `migrations/` and `web/`. Upload the archive and `tools/deploy-connector-backend.py` to the host; run the script with `sudo python3`, `--bundle` and the independently computed `--sha256`. It stops the service, backs up the application/environment/database, deploys with connector availability disabled, and checks the migration, row preservation, foreign keys, database integrity and HTTP readiness. The old native Node dependencies are retained. Backups must stay root restricted on encrypted storage.

For a release-only rollback, disable `CONNECTOR_ENABLED` first, restart to terminate access, restore the previous approved manifest and application release, and keep invitations disabled until checked. Versioned artifacts remain available for rollback; do not reuse their keys. If reverting migration 0009, enter a maintenance window, stop the service, save the current database for reconciliation, restore the pre-0009 database snapshot **and matching application/migrations**, discard only the stopped database's WAL/SHM files, verify ownership and restart. Restoring a snapshot discards subsequent writes; reconcile those records before reopening. Do not run the old application against a partially reverted schema.

## Logs, metrics and cost

CloudFront standard logging v2 delivers JSON to private encrypted bucket `masalapos-support-connector-logs-ej9w0mwvhhp9` with a 30-day expiry. Source `masalapos-connector`, destination `masalapos-connector-s3`, delivery `QpDuj7hqlvEJuzWd` are in `us-east-1`. The selected fields are `date`, `time`, `x-edge-location`, `sc-bytes`, `cs-method`, `cs(Host)`, `cs-uri-stem`, `sc-status`, `time-taken`, `x-edge-result-type`, `x-edge-request-id`. **Do not enable default/legacy logs or add query, cookie or referrer fields**, because invitation filenames are query parameters. Log delivery can be delayed.

Use built-in `AWS/CloudFront` metrics in `us-east-1`, dimensions `DistributionId=E3T73ML514FCC2`, `Region=Global`: Requests, BytesDownloaded, 4xxErrorRate, 5xxErrorRate and TotalErrorRate. A custom dashboard could not be created because the account's organization service-control policy explicitly denies `cloudwatch:PutDashboard`; ordinary distribution metrics remain the monitoring interface. Lightsail's restricted journal records connector status/byte counts and sanitized error classes. Caddy access logging is not enabled. Lightsail serves small JSON responses and redirects; binary transfers terminate at CloudFront/S3, and are verified independently there.

Budget for S3 object/version storage, PUT/GET requests, CloudFront HTTPS requests and viewer-region transfer, log delivery/storage, and any paid monitoring. **No promotional credits are assumed.** A 140 MB runtime downloaded by 1,000 uncached PCs transfers roughly 140 GB from the CDN, plus small stub downloads. Local cache reuse avoids another runtime download for the same release. Illustratively, $0.085/GB transfer would be about $11.90 for those runtime bytes before requests, taxes and logs; use the actual edge-region/account pricing. At an illustrative $0.023/GB-month S3 rate, ten 140 MB retained runtime versions cost about $0.03/month in object storage, excluding logs and old versions. Check [S3 pricing](https://aws.amazon.com/s3/pricing/), [CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/) and [CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/) before enabling rollout; India and other edge-region transfer prices can differ.
